# Exercise 1 - Default Policy

## Task

Explain the filter table's INPUT, OUTPUT, and FORWARD chains; choose default policies; permit internal servers to initiate outside connections and receive replies; permit Windows to use Telnet on Metasploitable with a MAC-address condition.

## 1. What each chain handles

| Chain | Traffic | Example in this lab |
|---|---|---|
| INPUT | Packets addressed to the gateway itself | An outside machine connects to `192.168.1.1`, or an inside machine connects to `192.168.2.1` |
| OUTPUT | Packets generated by the gateway itself | The gateway initiates a connection or responds to an accepted local request |
| FORWARD | Packets routed through the gateway to another host | Windows `192.168.1.12` connects to Metasploitable `192.168.2.10` |

The chain names are relative to the firewall machine. A packet entering the outside NIC and leaving the inside NIC traverses FORWARD; it is not filtered by INPUT and OUTPUT just because it enters and leaves interfaces. A forwarded packet has both `-i` and `-o`; a locally received packet has no outgoing interface at INPUT.

The filter table is the default table for `iptables`. NAT changes addresses/ports and does not replace a filter policy. Neither exercise requires NAT because both LANs can route via the gateway. [Chain and traversal reference](https://www.iptables.org/documentation/HOWTO/packet-filtering-HOWTO-7.html).

## 2. Chosen default policies

| Chain | Policy | Reason |
|---|---|---|
| INPUT | DROP | The gateway has no required incoming service in the assignment. Explicitly accept loopback and replies to gateway-originated connections. Configure via the VM console. |
| OUTPUT | ACCEPT | Allow the gateway's own administrative and diagnostic traffic. This assumes the gateway is trusted and keeps the lab focused on protecting LAN 1. |
| FORWARD | DROP | Deny traffic crossing the boundary unless a rule grants it. This makes outside access to the internal server an explicit exception. |

Commands expressing these defaults are:

```sh
iptables -P INPUT DROP
iptables -P OUTPUT ACCEPT
iptables -P FORWARD DROP
```

These are the policy choices, not a standalone safe application procedure. Use the complete rendered ruleset and backup/restore procedure in the lab README.

Default ACCEPT means traffic omitted from the rules is allowed, so an overlooked service remains reachable. Default DROP means omitted traffic is denied, so a missing exception may break functionality. OUTPUT DROP would impose tighter control on gateway egress, but would require explicit permits for DNS, updates, time synchronization, and other necessary traffic. OUTPUT ACCEPT does not grant forwarding: forwarded traffic still follows FORWARD DROP.

## 3a. Internal access to the outside network and replies

Figure 1 puts the inside LAN on `eth1` (`192.168.2.0/24`) and the outside LAN on `eth0` (`192.168.1.0/24`). The `/24` masks are an implementation assumption; confirm them on the VMs.

The relevant rules are:

```sh
iptables -A FORWARD -m conntrack --ctstate INVALID -j DROP
iptables -A FORWARD -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A FORWARD -i eth1 -o eth0 \
  -s 192.168.2.0/24 -d 192.168.1.0/24 \
  -m conntrack --ctstate NEW -j ACCEPT
```

The internal LAN may initiate new connections to the outside LAN. Once an allowed flow is tracked, ESTABLISHED permits its subsequent packets, including responses. RELATED permits traffic associated with an existing flow, such as an ICMP error. INVALID packets are discarded first.

For example, Metasploitable sends a TCP SYN to an outside service. The inside-to-outside NEW rule accepts it. The SYN-ACK returning to Metasploitable is accepted as part of the tracked connection. An unrelated outside SYN is NEW and must match a separate exception; it cannot use the reply rule to get inside.

The full solution also checks that forwarded traffic arriving on each interface has a source from that interface's subnet. This blocks cross-subnet source spoofing, but it does not prove the identity of an address within the correct subnet. The rule deliberately permits any protocol from internal hosts to the depicted outside LAN; a service-specific egress policy would be narrower. It does not grant unrestricted Internet access beyond this two-LAN topology.

Routing must also work. Enable IPv4 forwarding on the gateway and ensure outside hosts send traffic for `192.168.2.0/24` through `192.168.1.1`, while Metasploitable sends traffic for `192.168.1.0/24` through `192.168.2.1`. A firewall ACCEPT cannot repair missing routes.

## 3b. Windows Telnet with a MAC condition

Telnet uses TCP destination port 23. Windows is outside at `192.168.1.12` and Metasploitable is inside at `192.168.2.10`.

```sh
# Set WINDOWS_LAB_MAC to the actual Windows LAN 2 NIC MAC first.
iptables -A FORWARD -i eth0 -o eth1 \
  -s 192.168.1.12 -d 192.168.2.10 \
  -p tcp --syn --dport 23 \
  -m mac --mac-source "$WINDOWS_LAB_MAC" \
  -m conntrack --ctstate NEW -j ACCEPT
```

Both the IP and MAC conditions must match. SYN limits this opening rule to connection initiation; subsequent handshake and data packets use ESTABLISHED. Replies do not need a separate rule for source port 23. Opening every packet with `--sport 23` would be broader than accepting tracked replies.

Get the MAC from Windows' `ipconfig /all` and corroborate it with the gateway's neighbor table. The handout does not supply a MAC, so `02:00:00:00:01:12` in the sample is only the synthetic address used in the recorded demonstration.

The gateway can see Windows' Ethernet source MAC because Windows and `eth0` are on the same LAN. A MAC does not travel unchanged across routers; if Windows were behind another router, the gateway would see that router's MAC. MACs can also be spoofed. This condition satisfies the exercise and restricts this local link, but it is not cryptographic authentication. The check applies to new sessions, not every subsequent packet. [MAC matcher documentation](https://manpages.debian.org/trixie/iptables/iptables-extensions.8.en.html#mac).

## How to check on the course VMs

After applying exercise 1 using the lab README:

- From Windows: `telnet 192.168.2.10 23` should reach the Telnet service if it is running.
- From Kali: a new TCP/23 connection should time out.
- From Windows: a new TCP/22 connection should time out even if SSH is running.
- From the internal server: a connection to an active service on an outside host should work in both directions.
- From Kali: `ping 192.168.2.10` should fail before exercise 2 adds its exception.
- On the gateway: inspect `sudo iptables -nvL FORWARD --line-numbers`; matching rule counters should increase.

Use an active listening service for a denial check: an inactive service returning a connection refusal does not demonstrate firewall filtering. Telnet traffic is unencrypted; this exercise uses it only within the supplied lab topology.

The isolated Linux demonstration passed seven exercise 1 scenarios: internal TCP plus response; Windows TCP/23 with the right MAC; denied Kali TCP/23; denied Windows TCP/22 with a live listener; denied Windows TCP/23 with the right IP but wrong MAC; denied outside ping; and denied ping to the gateway itself.

The TCP/23 server was a banner listener, and Windows was a Linux stand-in. These results demonstrate firewall behavior, not a real Windows Telnet login or a run of the supplied course VMs. Raw evidence is in `Week 6/Lab/Evidence/namespace-demo.json` in the course repository.
