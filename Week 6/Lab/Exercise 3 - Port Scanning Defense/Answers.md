# Exercise 3 - Defense Against Port Scanning (Optional)

## Task

Use the `recent` module to track external connection attempts, choose a threshold and time window, and temporarily block a source that exceeds the threshold.

## Chosen policy

- Track forwarded **TCP SYN packets classified as NEW** from outside LAN 2 toward inside LAN 1.
- Allow the first 10 such packets within 60 seconds to continue to the ordinary access policy.
- On the 11th packet within that window, record the source in a separate ban list and drop the packet.
- Drop all forwarded outside-to-inside traffic from a banned source for 300 seconds since its last matching attempt. Continued traffic extends this interval.

“Continue to the ordinary access policy” does not grant access. For example, Kali's first ten SYNs still cannot open Telnet because the ACL in exercise 1 allows only Windows. The threshold and ban duration are choices made for this exercise; the handout does not specify them.

## Rule construction

The solution uses three custom chains and two recent lists. W6_ATTEMPTS stores attempt timestamps; W6_BANNED stores ban activity. The generated FORWARD jump runs before both the ICMP exception and ESTABLISHED acceptance.

```sh
iptables -N W6_SCAN_GUARD
iptables -N W6_SCAN_TRACK
iptables -N W6_SCAN_BAN

iptables -A W6_SCAN_GUARD -m recent --name W6_BANNED \
  --update --seconds 300 --rsource -j DROP
iptables -A W6_SCAN_GUARD -p tcp --syn \
  -m conntrack --ctstate NEW -j W6_SCAN_TRACK
iptables -A W6_SCAN_GUARD -j RETURN

# No target: record the packet, then evaluate the following rule.
iptables -A W6_SCAN_TRACK -m recent \
  --name W6_ATTEMPTS --set --rsource
iptables -A W6_SCAN_TRACK -m recent --name W6_ATTEMPTS \
  --rcheck --seconds 60 --hitcount 11 --rsource -j W6_SCAN_BAN
iptables -A W6_SCAN_TRACK -j RETURN

iptables -A W6_SCAN_BAN -m recent \
  --name W6_BANNED --set --rsource -j DROP

# Insert ahead of any rules that ACCEPT traffic from this source.
iptables -I FORWARD 1 -i eth0 -o eth1 \
  -s 192.168.1.0/24 -d 192.168.2.0/24 -j W6_SCAN_GUARD
```

Use the complete exercise 3 ruleset generated by the lab renderer when applying the solution; these commands explain the chain logic.

## How tracking and blocking work

1. Every outside-to-inside forwarded packet first checks W6_BANNED. `--update --seconds 300` matches a source whose most recent ban activity is within 300 seconds, updates its activity timestamp, and drops this packet.
2. A source outside an active ban proceeds. Only TCP NEW SYN packets go to W6_SCAN_TRACK; existing-flow packets and other protocols return to the normal rules.
3. `--set` records the current attempt in W6_ATTEMPTS. With no target, evaluation continues.
4. `--rcheck --seconds 60 --hitcount 11` checks the timestamp history without recording the same packet a second time. Because the current packet was already recorded, the first ten do not trigger the threshold; the eleventh does.
5. W6_SCAN_BAN records the source in W6_BANNED and drops the triggering packet. Subsequent outside-to-inside packets are dropped at the guard.
6. After 300 seconds without matching outside-to-inside traffic, the ban no longer matches. Normal policy evaluation resumes. The 60-second attempt window has also expired by then, so a fresh connection does not immediately retrigger the old threshold.

Separate attempt and ban lists keep the 60-second measurement window independent from the 300-second blocking interval. The use of `--update` implements a sliding inactivity ban, not a fixed five-minute period from the first detection. [Recent module documentation](https://manpages.debian.org/trixie/iptables/iptables-extensions.8.en.html#recent).

## What is actually detected

This is a rate-based heuristic for connection attempts, not a proof that a host is scanning ports. It counts matching SYN packets rather than unique ports or unique connections. A retransmitted SYN still classified NEW can count again. A legitimate burst of new TCP connections can also exceed the threshold.

Conversely, a slow scan staying below the threshold, scans distributed across several source IPs, UDP scans, and non-SYN TCP probes are not detected by this rule. Those still encounter the baseline default-deny policy, but this particular detector does not add them to its ban list. Shared source IPs and spoofed SYNs can cause collateral blocking. The recent lists are finite and their capacity depends on the kernel/module configuration.

The guard applies to forwarded traffic into LAN 1; it does not track attempts targeting the gateway itself. Gateway INPUT remains default DROP. Once a source is banned, the guard also blocks its otherwise legitimate replies and existing-flow traffic toward LAN 1. This is a deliberate broad response for the lab and may be disruptive in a production setting.

## Check on the course VMs

Apply `--exercise 3` through the lab README. From Kali in the supplied lab network, a TCP SYN scan against the lab server can generate the connection attempts:

```sh
sudo nmap -sS -Pn --max-retries 0 --max-rate 20 -p 1-30 192.168.2.10
ping -c 1 192.168.2.10
```

The scan is limited to the assignment's private Metasploitable address. Because the baseline already drops most ports, nmap reporting filtered ports alone does not prove the recent ban occurred. On the gateway inspect:

```sh
sudo iptables -nvL W6_SCAN_TRACK --line-numbers
sudo iptables -nvL W6_SCAN_BAN --line-numbers
sudo iptables -nvL W6_SCAN_GUARD --line-numbers
sudo cat /proc/net/xt_recent/W6_ATTEMPTS
sudo cat /proc/net/xt_recent/W6_BANNED
```

Kali's IP should appear in W6_BANNED after exceeding the threshold, and its ping should then fail despite exercise 2's normal permission. Windows should still reach permitted TCP/23. Stop all Kali traffic toward LAN 1 for more than 300 seconds, then retry a normal ping. Sending probes during that interval refreshes the sliding ban.

## Recorded outcome

The isolated Linux demonstration observed six successful scenarios:

1. Ten distinct new SYN packets from Kali did not create a ban.
2. The eleventh created a W6_BANNED entry for `192.168.1.11` using the actual 60/300-second policy.
3. Banned Kali ping was dropped.
4. Windows TCP/23 remained usable.
5. A separate run with shortened 2-second attempt / 3-second ban intervals activated a ban.
6. After four idle seconds in that shortened run, Kali ping worked again.

The full 300-second cooldown was not waited out. Its configured value and activation were checked; expiration behavior was demonstrated using shorter intervals. `rules.sample.v4` and the renderer retain 60/300, while the evidence field `shortened_cooldown_final_rules` explicitly shows the shorter final demo configuration. The supplied course VMs have not been run. See `Week 6/Lab/Evidence/namespace-demo.json` in the course repository.
